### 核心概念：为什么需要主从复制？

在开始之前，先明确主从复制的目的：

- **数据冗余**：实现数据的热备份，是持久化之外的另一种数据冗余方式。
- **故障恢复**：当主节点出现问题时，可以由从节点提供服务，实现快速的故障恢复。
- **负载均衡**：在主从复制的基础上，配合读写分离，可以由主节点提供写服务，由从节点提供读服务，分担服务器负载。
- **高可用基石**：主从复制是哨兵模式和集群模式能够实现的基础。

------

### 1. SYNC（全量复制）- Redis 2.8 之前

这是最早期、最原始的复制命令。

#### **工作流程**

1. **从节点启动或重连**：当从节点启动，或者与主节点的连接中断后重连时，它会向主节点发送一个 `SYNC` 命令。
2. **主节点执行 BGSAVE**：主节点收到 `SYNC` 命令后，开始在后台执行 `BGSAVE` 命令，生成当前数据库的 **RDB 快照文件**。
3. **缓存写命令**：在生成 RDB 文件的同时，主节点会将所有新接收到的、会修改数据集的**写命令**缓存到一个缓冲区中。
4. **发送 RDB 文件**：RDB 文件生成完毕后，主节点将其发送给从节点。
5. **从节点清空并加载**：从节点收到 RDB 文件后，会**清空自己的所有旧数据**，然后加载这个 RDB 文件，使自己的数据库状态更新至主节点执行 `BGSAVE` 时的状态。
6. **发送缓冲命令**：主节点将之前缓存在缓冲区里的所有写命令发送给从节点。
7. **从节点执行命令**：从节点执行这些写命令，最终使自己的数据库状态与主节点完全同步。

#### **SYNC 的严重缺点**

- **资源消耗巨大**：每次执行 `SYNC`，主节点都需要执行 `BGSAVE` 和传输 RDB 文件，这对 CPU、内存（子进程消耗）和磁盘 I/O 都是巨大的开销。如果从节点较多或网络频繁中断，主节点性能会受到严重影响。
- **效率低下**：即使连接只是短暂中断，从节点只是丢失了少量数据，也需要进行一次**全量同步**。这在网络不稳定的环境中是灾难性的。

> **比喻**：就像你有一本1000页的书（主节点），你朋友（从节点）只想看最新的第1001页。但SYNC的方式是，你把整本书重新复印一遍（生成RDB），然后寄给他，他再把旧书扔掉，用你的新复印本。

------

### 2. PSYNC（部分重同步）- Redis 2.8 引入

为了解决 SYNC 的效率问题，Redis 2.8 引入了 `PSYNC` 命令，它支持**全量复制**和**部分复制**。

#### **核心机制**

`PSYNC` 的实现依赖于三个关键概念：

1. **复制偏移量**
   - 主从节点都会维护一个复制偏移量。
   - 主节点每次向从节点传播 N 个字节的数据时，就将自己的复制偏移量加上 N。
   - 从节点每次收到主节点传来的 N 个字节的数据时，也将自己的复制偏移量加上 N。
   - 通过对比主从的偏移量，可以判断数据是否一致。
2. **主节点复制积压缓冲区**
   - 主节点维护一个固定长度的、先进先出（FIFO）的队列作为**复制积压缓冲区**。
   - 当主节点进行命令传播时，它不仅会将写命令发送给所有从节点，还会将写命令**写入**这个缓冲区。
   - 缓冲区中保存了最近一段时间主节点传播的写命令和对应的偏移量。
3. **服务器运行 ID**
   - 每个 Redis 节点，无论主从，都会在启动时自动生成一个唯一的运行 ID。
   - 从节点首次连接主节点时，会记录主节点的运行 ID。当断线重连后，从节点会向主节点发送之前记录的这个 ID。

#### **PSYNC 工作流程**

1. **从节点连接主节点**：从节点向主节点发送 `PSYNC` 命令，参数是 `主节点运行ID` 和 `当前从节点的复制偏移量`。
   - 如果是初次复制，则发送 `PSYNC ? -1`。
   - 如果是断线后重连，则发送 `PSYNC  `。
2. **主节点判断同步方式**：
   - **全量复制**：如果从节点传来的 `主节点运行ID` 与当前主节点 ID 不同，或者从节点提供的 `offset` 偏移量之后的数据已经不在主节点的**复制积压缓冲区**中（因为从节点断开太久，offset 已经被新数据覆盖挤出缓冲区），那么主节点会回复 `+FULLRESYNC  `，并进行一次全量同步（流程同 SYNC）。
   - **部分复制**：如果主节点 ID 匹配，并且 `offset` 之后的数据仍然存在于复制积压缓冲区中，那么主节点会回复 `+CONTINUE`，然后仅将从节点缺失的（从 `offset` 到缓冲区最新位置）那部分数据发送给从节点。

#### **PSYNC 的优点**

- 在绝大多数网络闪断的情况下，可以使用部分复制，极大地减少了全量复制的开销，提升了复制效率和整体性能。

> **比喻（续）**：现在你和朋友都有一个页码（复制偏移量），你身边还有一个便签本（复制积压缓冲区），记录了你最近新写的几页内容。当他短暂离开回来后，只需要告诉你他上次看到哪一页（offset）。如果那一页之后的内容还在你的便签本里，你只需要把便签本上那几页新的内容拍给他（部分复制）即可，不用再复印整本书。

### 3. PSYNC 2.0 - Redis 4.0 引入

`PSYNC` 虽然强大，但仍有一个场景会退化为低效的全量复制：**主节点发生故障切换**。

在 Redis 2.8~4.0 之间，如果主节点宕机，哨兵提升了一个从节点为新的主节点。此时，其他旧从节点向新主节点发起复制请求时：

- 因为新主节点的 `运行ID` 改变了，所以旧从节点发起的 `PSYNC` 请求会失败。
- 导致所有旧从节点都需要与新的主节点进行一次**全量复制**，即使它们的数据可能只差一点点。

**PSYNC 2.0** 主要解决了这个问题。

#### **核心改进**

1. **持久化复制信息**：
   - 将主节点的 `复制ID`（一个更大的概念，替代了单一的 `运行ID`）和当前的 `复制偏移量` 作为元数据，**持久化到 RDB 文件**中。
2. **新的复制ID**：
   - 每个主节点有两个复制ID：**主ID** 和 **副ID**。
   - 当节点成为主节点时，会生成一个主ID。
   - 在故障切换后，新的主节点会**继承**旧主节点的复制ID作为自己的**副ID**，同时自己生成一个新的**主ID**。
   - 这样，即使主节点变更，新的主节点也知道“上一个主节点是谁”。

#### **PSYNC 2.0 如何工作**

在故障切换场景下：

1. 旧从节点（现在要连接新主节点）发送 `PSYNC <旧主节点的运行ID> <自己的偏移量>`。
2. 新主节点收到请求后，会检查自己继承来的**副ID**是否与从节点传来的 `旧主节点运行ID` 匹配。
3. 如果匹配，并且从节点提供的 `offset` 仍然在新主节点的积压缓冲区中（新主节点在成为主节点之前，也记录了旧主节点的复制流），新主节点就会回复 `+CONTINUE`，进行**部分复制**。
4. 如果不匹配或 offset 丢失，则退化为全量复制。

#### **PSYNC 2.0 的优点**

- **大大提升了故障切换后的复制效率**：在主节点故障切换后，集群中的从节点有很大概率可以与新主节点进行部分重同步，避免了全量复制的巨大开销，使得故障恢复速度更快，对服务的影响更小。

### 总结对比

| 特性           | SYNC           | PSYNC                          | PSYNC 2.0                      |
| :------------- | :------------- | :----------------------------- | :----------------------------- |
| **引入版本**   | Redis 2.8 之前 | Redis 2.8                      | Redis 4.0                      |
| **同步方式**   | 仅全量复制     | 全量复制 + 部分复制            | 全量复制 + 部分复制（增强）    |
| **核心机制**   | RDB 快照       | 复制偏移量、积压缓冲区、运行ID | 持久化复制信息、主/副复制ID    |
| **资源消耗**   | 高             | 低（在网络闪断时）             | 极低（在故障切换时也大概率低） |
| **故障切换后** | -              | 必定全量复制                   | **大概率部分复制**             |

**演进思路**：从简单粗暴的**每次全量**（SYNC），到针对**网络中断的优化**（PSYNC），再到针对**主节点故障的优化**（PSYNC 2.0），Redis 主从复制的效率和鲁棒性在不断提升，为构建高可用的 Redis 集群奠定了坚实的基础。
