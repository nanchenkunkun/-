# 从 0 到 1 构建 RAG 系统：分步实施指南

## 一、开胃菜：全景图与六个概念

### 1.1 全景：一条离线链路 + 一条在线链路

一个能上线的 RAG 系统，完整链路是这样的：

```text
[离线·建库]                                    [在线·问答]
 数据采集 → 解析清洗 → 切分 → 向量化 → 入库      问题 → 查询改写 → 检索 → 重排 → 拼上下文 → 生成 → 引用
                                      │                                    │
                                      └──────── 索引（可增量更新）──────────┘
```

八个阶段：

| 阶段 | 做什么 | 交付物 | 大致耗时占比 |
| --- | --- | --- | --- |
| 1. 需求与设计 | 想清楚要回答什么类型的问题 | 问题类型清单 + 评估集雏形 | 10% |
| 2. 数据准备 | 采集、解析、清洗、切分 | 干净的 chunks（带 metadata） | **35%** |
| 3. 索引与存储 | 选 embedding、选向量库、建索引 | 可查询的索引 + 增量更新机制 | 10% |
| 4. 检索 | baseline → 混合检索 → 重排 | 召回率达标的检索器 | 20% |
| 5. 生成 | prompt 设计、上下文组装 | 带引用的答案 | 10% |
| 6. 服务化 | API、流式、缓存、监控 | 可调用的服务 | 10% |
| 7. 评估与调优 | 分层定位问题、迭代 | 评估报告 + 改进记录 | 持续 |
| 8. 上线与迭代 | 灰度、bad case 回流 | 稳定运行的系统 | 持续 |

**一个必须提前建立的认知**：数据准备（阶段 2）花的时间通常比写代码多得多。如果你打算三天上线，大概率第三天还在跟 PDF 里的表格较劲。把预期放对，后面不容易崩。

### 1.2 六个必须弄懂的概念

后面会反复用到这些词，先用大白话过一遍。**这六个词没搞明白，后面的章节会像看天书。**

#### ① 切分（chunk）：把书拆成卡片

模型的上下文窗口（一次对话里最多能塞进去的字数上限）装不下一整本手册；而且就算装得下，把整本书当成一个"检索单位"也毫无意义——你要找的只是某一页的某一段。

所以第一步是把文档拆成几百字的小块，每一块叫一个 **chunk**。类比：把一本手册拆成一张张卡片，每张卡片抄一段话。检索时找的是"最相关的几张卡片"，而不是"哪本书"。

#### ② Embedding（嵌入/向量）：给每段话标一个"语义坐标"

Embedding 是一个模型：输入一段文字，输出一串数字（常见是 1024 或 1536 个）。这串数字可以理解成这段文字在一个高维地图上的**坐标**。

关键特性：**意思相近的文字，坐标就靠得近。**"如何退货"和"退款流程"的坐标会挨在一起；"如何退货"和"火箭发射"会离得很远——尽管两者都带"如何"两个字。

这就是 RAG 能"按意思找"而不是"按字面找"的根本原因。

#### ③ 向量库（Vector Store）：存坐标，并且能秒找最近的邻居

普通数据库擅长"等于、大于、包含"，不擅长"离我最近的有哪些"。向量库专门干这件事：存几百万个坐标，还能在几十毫秒内找出离查询坐标最近的 k 个。

常见的：Chroma（本地开发）、PGVector（复用现成的 PostgreSQL）、Milvus / Qdrant（百万级以上）。

#### ④ 检索器（Retriever）与 top-k：一个函数，一句承诺

检索器就是一个黑盒：**输入一个查询，输出一堆相关段落。** 它背后可以是向量库、可以是关键词索引，也可以是两者混合——对你来说接口是一样的。

`k` 是取前几名。`k=5` 就是"给我最像的 5 段"。k 太小容易漏，太大则噪音多、还费 token——这是全程要反复拧的旋钮。

#### ⑤ 召回与重排（recall / rerank）：先粗筛，再精读

这是整套系统最重要的分工，用招聘类比最好懂：

- **召回（recall）**：HR 用关键词从 1000 份简历里粗筛出 100 份，目标是**宁滥勿缺**，别漏掉好人。
- **重排（rerank）**：面试官精读这 100 份，挑出最合适的 5 个，目标是**宁缺毋滥**，把凑数的剔掉。

对应到 RAG：先用便宜的向量检索捞 20 条（召回），再用更贵的 rerank 模型精读打分，只留 5 条（精排）。**这两个阶段的目标是相反的，所以必须分成两步做**——想让一个环节同时做到"不漏"和"不滥"，结果往往两头都做不好。

#### ⑥ 上下文（context）与幻觉（hallucination）：答案为什么会瞎编

**上下文**就是你最终塞进 prompt 的那段资料——检索回来的几段话拼在一起。模型只能看见这些，看不见整个知识库。

**幻觉**是模型在没有依据时，用自己的训练记忆编一个"听起来特别对"的答案。RAG 的全部意义就是用上下文压制幻觉；但如果你不明确要求"资料里没有就说没有"，模型依然会编——它天生倾向于给出一个答案，而不是承认不知道。

其余术语先混个眼熟，文中第一次出现时都会解释：

| 术语 | 一句话 |
| --- | --- |
| **BM25** | 关键词打分算法，不算语义，只数词出现得准不准、多不多 |
| **RRF** | 合并两路检索结果的规则：只看排名，不看分数 |
| **metadata** | 每个 chunk 附带的标签（出处、页码、部门、版本） |
| **prompt** | 发给模型的完整指令：规则 + 资料 + 问题 |
| **recall@k** | 前 k 条结果里命中正确段落的比例 |
| **faithfulness** | 答案里每句话能否在资料中找到依据 |

## 二、阶段 1：需求与设计

### 2.1 先回答三个问题

**问题一：用户会问什么类型的问题？**

| 问题类型 | 例子 | 对设计的直接影响 |
| --- | --- | --- |
| **单点事实** | "出差住宿上限多少？" | 切分可以小，top-1 就够，不需要复杂的检索链路 |
| **条款/条件类** | "跨境订单能退吗？" | 必须保证"例外条款"能被召回，切分要保留条款完整性 |
| **比较/汇总** | "三个版本的定价差异？" | 需要覆盖多份文档，k 要大；可能要"分头检索再汇总" |
| **多跳推理** | "A 项目的负责人是哪个部门的？" | 单次检索不够，得先查到负责人、再拿着名字查部门 |
| **流程/操作类** | "怎么申请报销？" | 需要步骤完整性，按标题结构切分优于按字数切分 |

这张表里出现了两个词，先简单交代：

- **2-Step RAG**：最朴素的形态——先检索，再生成。问一次、查一次、答一次，流程固定。
- **Agentic RAG**：把检索做成模型能主动调用的工具，由模型自己决定"要不要查、查几次、改个说法再查"。灵活，但也更慢、更贵、更难预测。

**如果你的问题 80% 是单点事实，用 2-Step 就够了——上 Agentic 是给自己找麻烦。**

**问题二：知识从哪来，多久变一次？**

- **来源**：PDF / Word / 网页 / Confluence / 数据库 / API？
- **更新频率**：静态制度文件（半年一次）vs 每日同步的业务数据（每天）——这决定索引是"全量重建"还是"增量更新"。
- **权限**：不同部门/客户看到的内容是否不同？如果是，metadata 里必须有权限字段，检索时必须带过滤（这是企业场景最容易漏的一环，后期补极其痛苦）。

**问题三：答错了会怎样？**

- 答错代价低（内部工具、FAQ）→ 2-Step RAG 起步。
- 答错代价高（合同、医疗、财务）→ 必须加校验层，或至少强制引用来源供人工核对。

### 2.2 先建评估集，再写代码

#### 什么是评估集

一张表，一行一条，核心就三列：**问题、标准答案、答案出自哪份文件**（再加序号和"类型"两列，方便统计覆盖率）。

| # | 问题 | 标准答案 | 出处 | 类型 |
| --- | --- | --- | --- | --- |
| 1 | 年假最多能结转几天？ | 5 天，且须在次年 3 月底前用完 | 员工手册.md | 正常 |
| 2 | 二线城市出差住宿标准？ | 400 元/晚，超标需部门负责人审批 | 差旅制度.md | 正常 |
| 3 | 跨境订单能无理由退货吗？ | 不能，跨境订单只支持质量问题退换 | 跨境业务规则.md | 边界/例外 |
| 4 | 公司有健身房吗？ | 资料未提及 → 应回答"没有相关信息" | — | 测拒答 |
| 5 | 那个还能用吗？ | 应要求澄清，或结合上文改写成完整问题 | — | 含糊 |

就这样，一张 Excel 或一个 JSONL 文件，**30 条起步**。

#### 为什么必须在写代码之前

先想一个场景：你花两周做完了搜索功能，老板问"效果怎么样"，你说"感觉还不错"。

**"感觉"不能当指标。** 这就是评估集存在的理由——它把你从"我觉得答得挺好"变成"50 条里 42 条答对，84%"。

两个类比：

- **考试**：不可能先考完再出答案，那样你永远不知道自己考了多少分。评估集就是那张提前备好的答案卷。
- **调收音机**：没有评估集去调 RAG，就像蒙着眼睛拧旋钮——手一直在动，但你既不知道是不是更清楚了，也不知道什么时候该停。

还有一个更隐蔽的好处：**写评估集的过程本身就是需求澄清。**

你要凑够 30 条问题，就不得不回答这些你原本会含糊过去的事——"用户会不会问跨文档的问题""有没有那种资料里根本没写的问法""同一个问题新旧两份文件都提到时算哪个对"。这些问题在写代码时想不起来，在写评估集时躲不掉。**很多需求漏洞，是在这一步被提前发现的，而不是上线后被用户发现的。**

反过来说，先写代码的典型结局是这样的：

```text
上线 → 用户说答得不对 → 你打开日志看
     → 分不清是"没搜到"还是"搜到了但答错"
     → 只能凭感觉改 prompt
     → 改完不知道变好还是变坏
     → 再改，再猜，两周过去，原地打转
```

#### 这 30 条从哪来

三个来源，按性价比排序：

1. **客服/同事的真实提问记录**（最值钱）。真实问法往往和你想的完全不同——你以为大家会问"年假结转规则"，实际问的是"去年没休完的假今年还能用吗"。
2. **业务方口述的"高频问题"**。找制度文档的负责人聊十分钟，比你自己编一小时强。
3. **自己按类型编**。前两类凑不够时补位。

关键是**四类都要有**，不能全是好答的：

| 类型 | 占比建议 | 作用 |
| --- | --- | --- |
| 正常问题 | 50% | 测基本盘，这类答不对说明系统还没做完 |
| 边界/例外 | 20% | 最容易答错的地方（"跨境订单除外"这种） |
| 资料里没有的 | 15% | 测它敢不敢说"不知道"，而不是瞎编 |
| 含糊/口语化 | 15% | 测查询改写是否有效 |

#### 三条实操建议

1. **标准答案从原文复制，别自己概括。** 你自己写的答案没有出处，后面就判断不了是"检索错了"还是"你记错了"。
2. **一定要填 `source` 列。** 它是后面区分"没找到"和"答错了"的唯一依据（第 8 章会用到）。
3. **不知道答案的问题，去问文档的主人，或者干脆只标出处、把答案留空。** 不要因为凑数而瞎填——一条错的标准答案，会长期误导你的优化方向。

#### 建好之后怎么用

- **建库跑通后立刻跑一次** → 拿到第一组数字（比如 recall@5 = 62%、忠实度 0.75）。这就是你的**基线**，后面所有优化都跟它比（62% 这个数怎么读，见 8.1）。
- **之后每次改动都重跑** → 换了切分参数、加了 rerank、改了 prompt，都跑一遍，涨了还是跌了一目了然。
- **上线后持续补** → 用户点踩的问题，人工核对后加进评估集。**这份表会越用越值钱**，最后变成你的回归测试集：任何改动跑一遍，就知道有没有把老问题改坏。

> 注意：评估集不是"建一次就完事"的文档，它是活的。第一次 30 条，三个月后 100 条，是很正常也很健康的状态。

#### 小结：评估集与基线，是一对

这两个词经常被混着说，但它们是两样东西：

| 概念 | 是什么 | 类比 |
| --- | --- | --- |
| **评估集** | 固定的题目 + 标准答案 | 考卷 |
| **基线（baseline）** | 第一次用这套卷子考出的分数，如 recall@5 = 62% | 第一次考试成绩 |

**评估集是尺子，基线是第一次量出来的刻度。** 后面每次验收，都是同一张卷子再考一次：新版本要 ≥ 62%，且不能是靠背答案背出来的。

把它当"后续验收的基准"没问题，但要知道它的边界：

- **只管效果，不管系统**。各阶段末尾那些 ✅（如"同一文档导入两次 chunk 数不变"）是过程检查，与评估集无关；性能、成本、权限、引用格式它也测不了。
- **只覆盖你抽样到的场景**。30 条测不出你没写进去的问题类型——它给的信心，上限就是样本的覆盖面。
- **会诱发"对着答案调参"**。建议留 10~20% 当 holdout，平时不看，只在版本上线前跑一次。
- **增补后不可直接比**。加了样本，分数口径就变了，所以给它打版本号（`eval_v1` / `eval_v2`），记录里写清"用的是哪一版卷子"。

> ✅ **阶段 1 验收**：有一份问题类型清单、明确了知识源与更新频率、有 ≥30 条带 source 的评估样本（四类齐全）。

## 三、阶段 2：数据准备（最重的一步）

### 3.1 采集与解析

不同格式的解析难度差异极大，这是踩坑重灾区：

| 格式 | 推荐做法 | 坑 |
| --- | --- | --- |
| 纯文本 / Markdown | 直接读 | 基本无坑 |
| PDF（文本型） | `pypdf` / `PyMuPDF` 抽取 | 双栏排版会串行；页眉页脚混进正文 |
| PDF（扫描件） | OCR（PaddleOCR / 云服务） | 识别错字、表格结构丢失 |
| Word | `python-docx` / `docx2txt` | 样式丢失，标题层级需自己还原 |
| HTML | `markdownify` / `trafilatura` | 导航栏、广告混入正文 |
| 表格（Excel/CSV） | 转 Markdown 表格或"一行一条记录" | 直接按字符切会把表切碎 |
| 图片/图表 | 多模态模型转描述 | 成本高，按需做 |

原则：**宁可少入库，不要脏入库。** 一段乱码进库，会长期污染检索结果，而且很难排查。

### 3.2 清洗

必须有一步确定性清洗，别指望模型"理解"垃圾文本：

```python
import re

def clean(text: str) -> str:
    text = re.sub(r"\n{3,}", "\n\n", text)             # 压缩空行
    text = re.sub(r"^\s*\d+\s*$", "", text, flags=re.M) # 去掉孤立页码
    text = re.sub(r"第\s*\d+\s*页\s*(共\s*\d+\s*页)?", "", text)
    text = re.sub(r"[ \t]{2,}", " ", text)              # 压缩空格
    text = re.sub(r"[\u200b-\u200f\ufeff]", "", text)   # 去零宽字符
    return text.strip()
```

再加两条：

- **去重**：同一份文档多个版本、同一段落重复出现，会让检索结果"全是同一段"，浪费 k。
- **过滤过短 chunk**：少于 20 字的片段（如"目录""注意事项"）基本没有检索价值，直接丢。

### 3.3 metadata 设计（决定后期能不能救）

建库时多花一小时，调试时省十小时。最小可用的 schema：

```python
metadata = {
    "source": "员工手册.pdf",        # 出处（必填，用于引用）
    "page": 12,                      # 页码/位置
    "section": "第三章 假期管理",     # 章节标题（按结构切分时可得）
    "doc_type": "policy",            # 文档类型，便于分类检索
    "version": "2024-06",            # 版本/生效日期，用于时效过滤
    "department": "hr",              # 归属部门
    "acl": ["hr", "all"],            # 访问权限（企业场景必需）
}
```

没有 `section`，你后面想按章节聚合上下文就只能靠猜；没有 `version`，新旧制度冲突时无法裁决；没有 `acl`，越权检索就是安全事故。

### 3.4 切分：RAG 效果的第一决定因素

**优先级：按结构切 > 按语义切 > 按固定字数切。** 字符切分是最后手段。

先解释三个参数，后面代码里会用到：

| 参数 | 含义 | 为什么要管它 |
| --- | --- | --- |
| `chunk_size` | 每块最大多少字 | 太大：一个坐标混了好几个主题，匹配变模糊；太小：语义不完整 |
| `chunk_overlap` | 相邻两块重叠多少字 | 防止关键句正好被切在边界上，前半句和后半句进了不同块 |
| `add_start_index` | 记录这块在原文的位置 | 出问题时能回到原文核对，排查必备 |

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter, MarkdownHeaderTextSplitter

# 推荐一：有标题结构的文档（Markdown / 转成 Markdown 的文档）
md_splitter = MarkdownHeaderTextSplitter(
    headers_to_split_on=[("#", "h1"), ("##", "h2"), ("###", "h3")],
)
# 效果：每个 chunk 自带 section 路径，metadata 里就有"第几章第几节"

# 推荐二：无结构纯文本
text_splitter = RecursiveCharacterTextSplitter(
    chunk_size=400,          # 中文经验值 300~500，比英文的 1000 小
    chunk_overlap=50,        # 约 10~15%
    add_start_index=True,
    separators=["\n\n", "\n", "。", "；", "，", " ", ""],  # 优先在语义边界断开
)
```

三个关键判断：

1. **中文 chunk 要比英文小**。中文信息密度高，1000 字符的中文 chunk 往往包含 3~5 个主题，向量会被"平均"成一个模糊的点。
2. **切分要保住"条件"**。条款类文档如果按字数切，很容易把"……不适用。"这半句切到下一个 chunk，导致检索到的规则丢失了限定条件——这是错误答案的头号来源。
3. **chunk 太小也不行**。太碎会让答案缺上下文（"最多结转 5 天"不知道是年假还是调休）。

那怎么办？答案是**用两种大小，各干各的活**。

先搞清楚为什么"只能用一种大小"会打架：**每个 chunk 只对应一个向量，而向量是这段文字的"平均意思"。**

- 1000 字的块里往往讲了四五件事（年假、调休、病假、婚假），压成一个向量后就变成"大杂烩的平均"——你问"年假能攒吗"，它跟你的距离并不近，反而可能被别的块盖过。
- 但全切成 200 字，又会切在句子中间：小块只剩"最多结转 5 天"，模型不知道说的是年假还是调休，而"须在次年 3 月底前用完"这半句躺在隔壁块里，没被取回来。

**检索希望块小（意思纯、匹配准），生成希望块大（上下文全）。这两个要求正好相反，那就别用同一个块。**

**父子切分（small-to-big）**：入库时按两种粒度各切一遍，用一个 ID 关联。

```text
            原文《员工手册》
                   │
        ┌──────────┴──────────┐
    切 200 字（子块）      切 1000 字（父块）
        │                       │
   算向量存进向量库        原样存进文档库(KV)
        │                       │
   每个子块多带一个 parent_id ──► 指向它所属的父块

检索：问题 → 在子块里找最近的 3 条 → 读出它们的 parent_id
      → 去文档库取回对应的父块（同一父块只取一次）→ 拼进 prompt
```

一句话记：**子块负责被找到，父块负责被读懂。**

类比图书馆：目录卡片上只写一行书名和关键词（方便你快速翻找），但真正借给你的是整本书（方便你读）。不会为了好找把书撕成单页，也不会为了好读只给你一个书名。

```python
from langchain.retrievers import ParentDocumentRetriever
from langchain.storage import InMemoryStore
from langchain_chroma import Chroma

child_splitter = RecursiveCharacterTextSplitter(chunk_size=200)    # 用来检索（精准）
parent_splitter = RecursiveCharacterTextSplitter(chunk_size=1000)  # 用来喂给模型（完整）

retriever = ParentDocumentRetriever(
    vectorstore=Chroma(embedding_function=embeddings, collection_name="child"),
    docstore=InMemoryStore(),          # 生产换成 Redis / MongoDB
    child_splitter=child_splitter,
    parent_splitter=parent_splitter,
)
retriever.add_documents(docs)
# 检索时匹配的是 200 字的小块，返回的是所在 1000 字的父块
```

三个必须注意的地方（都是实际会踩的坑）：

| 坑 | 说明 |
| --- | --- |
| **父块要去重** | 3 个子块可能同属一个父块，不去重就是同一段文字塞 3 遍，token 直接翻三倍 |
| **父块别太大** | 1000 字已接近上限。k=5 个子块 → 最多 5 个父块 → 5000 字进 prompt，再多就挤爆上下文预算 |
| **文档库要持久化** | 示例里的 `InMemoryStore` 进程一重启就没了，生产换 Redis / MongoDB，key 就是父块 ID |

收益在于：**检索精度和上下文完整性不再是二选一。** 原来调 `chunk_size` 是在两者之间左右挪，现在两头都要到了，代价只是多存一份原文——文本本身很小，这点存储不是问题。

> ✅ **阶段 2 验收**：随机抽 10 个 chunk 检查——无乱码、无页眉页脚、语义完整、metadata 齐全；用评估集里的问题手查 chunks，相关段落能被找到。

## 四、阶段 3：索引与存储

### 4.1 选 embedding 模型

用 1.2 里的说法：embedding 模型决定了"把文字画在哪张地图上"。换模型 = 换了一张完全不同比例尺的地图，旧坐标在新地图上没有意义。

| 场景 | 推荐 | 说明 |
| --- | --- | --- |
| 快速验证 | `text-embedding-3-small` | 便宜、够用 |
| 中文为主 | `bge-m3`、`qwen3-embedding`、`text-embedding-3-large` | bge-m3 支持多语言 + 长文本，可本地部署 |
| 私有化/合规 | `bge-m3`（本地） | 无外网依赖，数据不出内网 |
| 多语言混合 | `bge-m3` / `multilingual-e5-large` | 跨语言检索 |

**两条硬规则**：

1. **入库和查询必须用同一个 embedding 模型**。换了模型必须全量重建索引，否则向量空间不兼容，检索结果等于随机。
2. **先在小样本上验证**。拿 20 条评估问题跑一遍，看 top-5 里有没有正确段落——这一步 30 分钟，能避免选错模型后返工一整天。

### 4.2 选向量库

| 规模 | 推荐 | 理由 |
| --- | --- | --- |
| 原型 / < 10 万 chunk | Chroma、`InMemoryVectorStore` | 零运维，几行代码 |
| 已有 PostgreSQL | PGVector | 复用地基设施，事务/权限直接复用 |
| 百万级以上 | Milvus、Qdrant | 分布式、高性能、强过滤 |
| 多租户 SaaS / 库内混合检索 | Weaviate | BM25+向量单查询融合、内置向量化模块、原生多租户 |
| 全托管 | Pinecone、OpenSearch | 省运维，按量付费 |

**Weaviate 和上面几个不是同一类东西。** 它把"生成向量 + 混合检索 + 重排"都收进了库里：入库时由模块直接调 embedding 模型（不用自己维护管线），查询时一句 `hybrid(query=..., alpha=0.7)` 就完成 BM25 与向量的融合，不必像 5.2 那样在应用层拼 `EnsembleRetriever`。它的多租户是**原生**的——每个 tenant 独立 shard、共享 schema，适合"每个客户一套知识库"的 SaaS。

代价有三点：融合逻辑锁在库内，调参空间不如应用层自己拼；schema 要预先定义，字段变更比 schema-less 麻烦；运维比 Chroma 重（要跑服务、管 schema）。判断标准很直接：**需要原生多租户、或不想维护 embedding 管线，选它；只想快速验证，Chroma 更省事；已有 Postgres 且量不大，PGVector 仍是组件最少的方案。** 它和 Qdrant 最像，区别是 Qdrant 更"纯引擎"（向量你自己算好喂进去），Weaviate 更"全家桶"。

### 4.3 建索引

```python
from langchain_chroma import Chroma
from langchain_openai import OpenAIEmbeddings

embeddings = OpenAIEmbeddings(model="text-embedding-3-small")
vector_store = Chroma(
    collection_name="kb_v1",
    embedding_function=embeddings,
    persist_directory="./chroma_db",
)

# 批量入库（比逐条快一个数量级）
BATCH = 100
for i in range(0, len(chunks), BATCH):
    vector_store.add_documents(chunks[i:i + BATCH])
```

上面这段能让库跑起来，但撑不住长期维护。工程上还得补三件事，分别解决"重复""过期""回不去"。

#### 4.3.1 稳定 ID：让重复导入不重复

问题很朴素：导入脚本跑两遍，库里就有两份。

不要用随机 UUID（每次生成都不一样），要用**由内容算出来的 ID**：

```python
import hashlib
from langchain_core.documents import Document

def chunk_id(doc: Document) -> str:
    # 用内容本身算指纹：内容没变 → ID 必然没变
    return hashlib.sha1(doc.page_content.encode("utf-8")).hexdigest()[:16]

ids = [chunk_id(d) for d in chunks]
vector_store.add_documents(chunks, ids=ids)   # 同 ID 再写一次是覆盖，不是新增
```

第二遍跑的时候，每块算出来的 ID 和库里那条一模一样，写进去就是覆盖，总数不变。这就是**幂等**：执行一次和执行十次结果一样。

**但这里有个关键局限，多数教程不讲**：内容 hash 只能保证"同样的内容不重复"，保证不了"改过的文档不留旧碎片"。你把某一段改了，新内容算出新 ID，旧 ID 那条还躺在库里——检索时新旧两版一起被捞出来，模型看到两段自相矛盾的话，答得比没有还糟。

所以 ID 只是第一半，第二半必须靠按 `source` 删除。**只做稳定 ID 就上线，一个月后库里的重复和过期段落能占到三成。**

#### 4.3.2 按 source 同步：别全量重建，也别只插不删

目标很明确：文件改了要更新，文件删了要从库里消失，没改的一个都别动。

第一步，判断"变没变"。别用文件修改时间（`mtime` 不可靠：复制文件会变、git 切分支也会变），用内容哈希。为此维护一张**索引清单**：

| 字段 | 用途 |
| --- | --- |
| `source` | 文件路径 / URL，唯一键 |
| `content_hash` | 整个文件的 sha256，判断变没变 |
| `chunk_ids` | 这份文件切出的所有 chunk ID，删除时用 |
| `embedding_model` | 建库用的模型名，不一致的库不能混查 |
| `indexed_at` | 最后同步时间 |

清单放哪都行——SQLite、一张业务表、甚至一个 JSON 文件。原型阶段 JSON 足够，别为了这个再引入新组件。

第二步，四类情况分开处理：

```python
import hashlib, json, pathlib
from datetime import datetime

def file_hash(p: pathlib.Path) -> str:
    return hashlib.sha256(p.read_bytes()).hexdigest()

def sync_index(src_dir: str, manifest_path: str = "index_manifest.json"):
    mf = pathlib.Path(manifest_path)
    manifest = json.loads(mf.read_text("utf-8")) if mf.exists() else {}

    current = {str(p): file_hash(p)
               for p in pathlib.Path(src_dir).rglob("*") if p.is_file()}

    # ① 源文件已删除 → 清掉它的全部 chunk
    for src in set(manifest) - set(current):
        vector_store.delete(where={"source": src})
        del manifest[src]

    for src, h in current.items():
        if manifest.get(src, {}).get("content_hash") == h:
            continue                                   # ② 没变化，跳过
        # ③ 新增或已修改：先删旧、再插新，顺序不能反
        vector_store.delete(where={"source": src})
        docs = load_and_split(src)                     # 前面写的加载 + 切分
        ids = [chunk_id(d) for d in docs]
        vector_store.add_documents(docs, ids=ids)
        manifest[src] = {
            "content_hash": h,
            "chunk_ids": ids,
            "embedding_model": "text-embedding-3-small",
            "indexed_at": datetime.now().isoformat(),
        }

    mf.write_text(json.dumps(manifest, ensure_ascii=False, indent=2), "utf-8")
```

三个容易写错的地方：

- **先删后插，顺序不能反**。反过来就变成"新的插进去、旧的还留着"——新 ID 覆盖不了旧 ID，等于白做。删的时候**按 `source` 整份删**，别只删变化的那几块，否则切分边界一挪，残留满地。
- **源文件被删的处理最容易漏**（代码里的 ①）。漏了的话，过期内容还在被检索，用户点引用链接还会 404。
- **`delete(where=...)` 不是所有向量库都支持**。Chroma、PGVector 可以；不支持的（比如某些版本的 FAISS）就用清单里的 ID 精确删：`vector_store.delete(ids=manifest[src]["chunk_ids"])`。这也是清单里要存 `chunk_ids` 的原因之一。

#### 4.3.3 版本化：让"重来一次"可以回滚

换 embedding 模型、改切分策略，都必须全量重建索引。问题是：重建期间旧库不能停服，而新库也可能更差。

做法是**新建一个 collection，而不是在原来那个上面重建**：

```text
kb_v1（线上） ──重建──► kb_v2（离线跑评估集）
                            │ 验证通过
                            ▼
                      改配置切流量 → kb_v2 上线
                            │ 发现问题
                            ▼
                      改回配置 → 秒回滚到 kb_v1
```

落地就两步：

1. 建库脚本接受版本参数：`python build_index.py --version v2 --embedding bge-m3`
2. 查询侧从配置读 collection 名（`KB_COLLECTION=kb_v2`），不写死在代码里

旧版本别急着删，留一到两周当回滚位。这点存储成本，远低于一次事故的成本。

三件事合起来记：**ID 管"不重复"，source 同步管"不过期"，版本管"回得去"。** 缺任何一个，库都会在几周后变得不可信。

> ✅ **阶段 3 验收**：索引可查询；同一份文档连续导入两次，chunk 总数不变（幂等）；改一份文档后重跑，只更新该文档且无残留；删一个源文件后重跑，它的 chunk 全部消失；能通过改配置在 `kb_v1` / `kb_v2` 之间切换。

## 五、阶段 4：检索

这一章只干一件事：**把该看的那几段资料，稳稳送进模型的视野。**

检索出问题，翻来覆去只有三种病，对应三种药：

| 症状 | 怎么确认 | 该用哪个 |
| --- | --- | --- |
| **漏了**：该看的段落根本没被取回 | 正确段落在 top-20 里也找不到 | 混合检索（5.2）、查询改写（5.4） |
| **排错了**：找得到，但排在第八九名，进不了前五 | top-5 没有，top-20 有 | rerank（5.3） |
| **混进来了**：结果里有不该看的东西 | 越权文档、过期版本出现在结果里 | metadata 过滤（5.5） |

**先确诊，再下药。** 四个一起上，你既不知道哪个起了作用，也不知道多花的钱值不值。一次只加一个，加完重跑评估集，数字涨了留下，没涨撤掉。

### 5.1 先跑一个 baseline

**baseline（基线）**就是不加任何花招的最朴素版本：问题直接丢给向量检索，取前 5 条，喂模型。它不需要效果好，它的作用是当**参照物**。

```python
retriever = vector_store.as_retriever(search_kwargs={"k": 5})
```

跑一遍评估集，得到一个数字，比如 recall@5 = 62%。往后每改一处都跟它比："加了 rerank 之后 78%，涨 16 个点"——这话能说清楚。没有基线，你只能说出"感觉好点了"。

顺便把病根看清楚。那 50 条里漏掉的 19 条，逐条把 top-20 拉出来看：

- 正确段落在 top-20 里 → **排错了**，去 5.3 加 rerank
- 不在 → **真找不到**，去 5.2 或 5.4

这一步花二十分钟，能省掉后面一整天乱试。

### 5.2 武器一：混合检索（治"漏了"）

先说 **dense（稠密检索）**：就是前面讲的向量检索，把问题也变成坐标，找最近的段落。它擅长"意思相近"——"怎么退款"能匹配到"退货流程"，因为这两句在语义地图上挨着。

**BM25** 正好相反：它不理会语义，只数词。你问题里带了"X200"和"保修"，它就给同时含这两个词的段落打高分；"X200"在整个库里越罕见，命中它的段落加分越多——因为罕见词更能区分。

为什么两个都要上？因为向量检索有两个天生的盲区：

- **精确匹配**：型号 `X200`、订单号、人名。向量模型会把 `X200` 和 `X210` 看成"差不多的东西"，而业务上这是两个产品。
- **罕见新词**：模型训练时没见过的新术语，它给出的坐标本身就不靠谱。

看个具体场景。库里有两段：

```text
A: "X200 整机保修 2 年，电池 1 年。"
B: "X210 整机保修 3 年，含意外损坏。"
```

问"X200 保修多久"，向量检索很可能把 B 排在前面——两段结构、用词几乎一样，坐标几乎重合，只能靠那一点点差异区分。而 BM25 一眼看出 B 里压根没有"X200"这个词，直接把它压下去。两路一合，A 就上来了。

```python
from langchain_community.retrievers import BM25Retriever
from langchain.retrievers import EnsembleRetriever

bm25 = BM25Retriever.from_documents(chunks)
bm25.k = 5                                    # 中文建议配 jieba 分词，否则按字切效果差
dense = vector_store.as_retriever(search_kwargs={"k": 5})

hybrid = EnsembleRetriever(
    retrievers=[bm25, dense],
    weights=[0.4, 0.6],                       # 内部用 RRF 融合，无需调分数的量纲
)
```

**RRF（Reciprocal Rank Fusion）** 是合并两路结果的办法，规则简单到粗暴：**不看分数，只看名次。**

某段在某一路排第 1，得 1/(60+1) 分；排第 2，得 1/(60+2) 分；两路得分相加，重新排序。还是上面那个例子：

| 段落 | 向量检索名次 | BM25 名次 | 合计得分 | 最终 |
| --- | --- | --- | --- | --- |
| A（X200 保修 2 年） | 第 3 → 1/63 ≈ 0.0159 | 第 1 → 1/61 ≈ 0.0164 | **0.0323** | 第 1 |
| B（X210 保修 3 年） | 第 1 → 1/61 ≈ 0.0164 | 没进前 5 → 0 | 0.0164 | 第 2 |

A 在两路都不算差，加成之后反超了只在单路拿第一的 B。这就是融合的价值：**一路的偶发失误，会被另一路纠正。**

为什么不直接把分数加起来？因为量纲不可比——向量给的是 0~1 的相似度，BM25 给的是 0~30 的关键词分，放一起加毫无意义。"名次"则是同一套语言，`weights` 只需表达偏好（我信向量多一点），不用精确调数值。

### 5.3 武器二：重排（治"排错了"）

先记住这个分工：

```text
向量/BM25 各取 top-20  →  RRF 合并  →  rerank 精排  →  取 top-5
    宁滥勿缺（怕漏）                    宁缺毋滥（剔除噪音）
```

为什么 rerank 更准？因为两者干活的方式根本不同：

- **向量检索是"各看各的"**：问题和文档分别压成一个坐标，再比距离。它胜在快，几百万条也扫得动。
- **rerank 是"放一起读"**：把问题和这一段拼成一对，一起送进模型，直接判断"这段能不能回答这个问题"。它看得细、判得准，但每一条都要跑一次模型。

一句话说透这个差别：**向量检索里，问题和文档从没见过面。** 两者各自被压成一千多个数字，然后隔空比距离。压缩是有损的——"X200 还是 X210""除跨境订单外不适用"这类关键差异，在压成坐标时就被抹平了。rerank 则是把两者摆在一起逐字读，所以它看得出"这段话的主语不是你要的那个"。

拿刚才的例子走一遍：问"X200 保修多久"，向量检索很可能把"X210 整机保修 3 年"排在第 1（句式太像，坐标几乎重合），把"X200 整机保修 2 年"排在第 3。rerank 逐字比对后认出第 1 名讲的是 X210，把它压下去、第 3 名提到第 1——这就是"排错了"被治好。

所以它只能用在少量候选上：**20 条进去，5 条出来。** 反过来看更清楚——为什么不让 rerank 直接扫全库？10 万条就是 10 万次模型调用，钱和时间都不允许。先粗筛再精读，是搜索系统的老套路。

**它的边界比它的能力更重要：rerank 只能给已有的候选重新排序，变不出新文档。** 正确段落在 top-20 里，它救得回来；top-20 里压根没有，加它只是把 20 条垃圾重排一遍。所以加之前先确认一件事：漏掉的题，在 top-20 里找得到吗？找不到就先修召回，别急着加它。

这 20 次调用值不值？通常非常值：**如果只能加一个优化，就加它**——收益最大，改动最小。

```python
from langchain.retrievers import ContextualCompressionRetriever
from langchain_cohere import CohereRerank

reranked = ContextualCompressionRetriever(
    base_retriever=hybrid,
    base_compressor=CohereRerank(model="rerank-multilingual-v3.0", top_n=5),
)
```

开源替代：`bge-reranker-v2-m3`，中文效果好，能本地跑，不必把文档发出去。

### 5.4 武器三：查询改写（也治"漏了"）

有时候不是检索不行，是**问题本身没法检索**。

多轮对话里最明显："那它多少钱？"——"它"是谁？库里没有任何一段文字包含这句话，向量再强也匹配不到。

```text
上一轮：X200 的延保服务怎么买？
这一轮：那它多少钱？
改写后：X200 延保服务的价格是多少？
```

改写就是把这句"人话"翻译成"检索能用的查询"：补全指代、去掉口语、保留关键实体（型号、部门、时间）。

```python
REWRITE_PROMPT = """把用户问题改写成一句可独立检索的查询：补全指代、去掉口语、保留关键实体。
只输出改写后的查询。

对话历史：
{history}

用户问题：{question}"""

def rewrite_query(question: str, history: str = "") -> str:
    return llm.invoke(REWRITE_PROMPT.format(question=question, history=history)).content.strip()
```

进阶玩法是 **Multi-Query**：让模型把同一个问题换三个角度写一遍，分别检索，结果合并。其中**固定留一条专门问"例外/适用条件"**：

```text
主查询：跨境订单能退货吗
第 2 条：跨境订单退货需要什么材料
第 3 条：跨境订单退货的例外情形有哪些   ← 专门盯例外
```

这条几乎零成本，却能救回大量"规则找到了、例外漏掉了"的错误。前面反复提过，条款类文档答错，一半以上是缺了例外。

### 5.5 武器四：metadata 过滤（治"混进来了"）

这个不叫优化，叫**门槛**。前三个决定"答得好不好"，这个决定"答得对不对、该不该答"。

```python
retriever = vector_store.as_retriever(
    search_kwargs={
        "k": 5,
        "filter": {"department": {"$in": user.departments}, "version": "2024-06"},
    }
)
```

两个场景必须做：

- **权限**：用户只能看自己部门的文档。不过滤，等于把别的部门的内部资料喂给了模型——这是事故，不是 bug。
- **时效**：新旧制度同时被检索，模型会随机挑一个信。新版发布后，旧版必须靠 `version` 字段挡在门外。

一个容易踩的细节：过滤要在**检索时**做（`filter` 参数），不能检回来再筛。先取 5 条再筛掉 3 条，只剩 2 条可用，等于白检。

> ✅ **阶段 4 验收**：在自己评估集上 recall@5 ≥ 80%；越权问题检不回无权文档；旧版本内容不出现在结果里；每加一个改动，都有改动前后的分数记录。

## 六、阶段 5：生成

### 6.1 prompt 的四条铁律

```python
PROMPT = """你是{company}的制度问答助手。请严格依据【资料】回答。

规则：
1. 只使用【资料】中的信息，不要依赖你的常识或训练数据补充。
2. 【资料】不足以回答时，直接回答"现有资料未涵盖该问题"，并说明缺什么。
3. 每个结论后用 [编号] 标注来源，如 [1][3]。
4. 涉及条件、例外、时限的，必须完整转述，不得省略。

【资料】
{context}

【问题】
{question}
"""
```

四条规则各自解决一个问题：

| 规则 | 解决的问题 |
| --- | --- |
| 只用资料 | 模型用训练知识"补充"，产生看似合理但无出处的幻觉 |
| 不足就说不足 | 模型硬答，编造答案（**拒答能力是 RAG 的核心指标**） |
| 标注来源 | 无法核对，用户不敢信；也无法定位 bad case |
| 条件例外完整转述 | 只答"可以"，漏掉"但跨境订单除外" |

### 6.2 上下文组装

拼接不是简单 `"\n".join()`，四个细节：

```python
def build_context(docs):
    parts, seen = [], set()
    for i, d in enumerate(docs, 1):
        # 1) 去重：同一段内容可能被多路检索重复召回
        key = d.page_content[:80]
        if key in seen:
            continue
        seen.add(key)
        # 2) 标注编号 + 出处，编号供答案引用
        header = f"[{i}] 来源：{d.metadata['source']}"
        if d.metadata.get("section"):
            header += f" / {d.metadata['section']}"
        parts.append(f"{header}\n{d.page_content}")
    return "\n\n".join(parts)
```

另外两点：

3. **按相关度排序，最相关的放最前**（模型对上下文开头更敏感）。
4. **控制总长度**。不是 k 越大越好，8 个 500 字的 chunk 已经 4000 字，噪音会淹没信号。宁可 k=5 加 rerank。

### 6.3 串成一条链

```python
from langchain_core.output_parsers import StrOutputParser
from langchain_core.runnables import RunnablePassthrough

chain = (
    {
        "context": (lambda q: reranked.invoke(q)) | build_context,
        "question": RunnablePassthrough(),
    }
    | PROMPT
    | llm
    | StrOutputParser()
)

answer = chain.invoke("年假可以攒到明年吗？")
```

> ✅ **阶段 5 验收**：抽 20 条评估问题人工看——答案有依据、有引用、资料没有时敢说"没有"、条件例外不缺。

## 七、阶段 6：服务化

### 7.1 一个够用的 API

```python
from fastapi import FastAPI
from fastapi.responses import StreamingResponse

app = FastAPI()

@app.post("/chat")
async def chat(req: ChatRequest, user=Depends(get_current_user)):
    # 1) 查询改写（多轮时带上历史）
    query = rewrite_query(req.question, req.history)
    # 2) 检索（带权限过滤）
    docs = await retriever_with_filter(user).ainvoke(query)
    # 3) 流式生成，先返回引用、再返回正文
    async def gen():
        yield json.dumps({"sources": [d.metadata["source"] for d in docs]}) + "\n"
        async for chunk in (PROMPT | llm | StrOutputParser()).astream(
            {"context": build_context(docs), "question": req.question}
        ):
            yield json.dumps({"delta": chunk}) + "\n"
    return StreamingResponse(gen(), media_type="application/x-ndjson")
```

三个工程要点：

- **先返回引用再流式吐正文**：用户能立刻看到"答案基于哪 3 份文件"，等待焦虑大幅下降。
- **检索要有超时和降级**：向量库超时 2s 就返回"检索服务繁忙"，别让整个请求挂死。
- **缓存**：`(query, 权限范围)` 的检索结果缓存 5 分钟，重复问题能省掉 80% 的检索开销。

### 7.2 监控三件事

| 指标 | 为什么看它 |
| --- | --- |
| 检索耗时 P95 / 生成耗时 P95 | 定位性能瓶颈在哪一段 |
| 空召回率（top-1 分数低于阈值） | 升高说明知识库有盲区，或用户问了新话题 |
| 拒答率 + 点踩率 | 拒答率突增=检索坏了；点踩集中=生成质量问题 |

> ✅ **阶段 6 验收**：接口能流式返回、能带引用、有超时降级；日志里能还原"某次请求检索了什么、答了什么"。

## 八、阶段 7：评估与调优（决定上限）

### 8.1 分两层评估，别混在一起

RAG 出错只有两种：**没找到**，或**找到了但答错**。必须分开测，否则你会优化错方向——把"检索没找到"的问题当成"模型不会答"去改 prompt，永远改不好。

**检索层**（不涉及 LLM，便宜、可高频跑）：

**先解释 recall@k（召回率）**：一句话——**该找到的资料，找到了多少。**

拆开看这个符号：

- **recall（召回率）**：该被找到的，实际找到了多少的比例
- **@k**：只看前 k 条结果（因为最终只把这 k 条喂给模型）
- **所以 recall@5 = 62% 的意思是**：50 个测试问题里，有 31 个的正确答案出现在了前 5 条里

```text
评估集 50 条问题，逐条去检索，每次取回 5 条
├─ 31 条：正确的那段资料，在这 5 条里面      ← 命中
└─ 19 条：前 5 条里压根没有正确资料          ← 漏了
recall@5 = 31 / 50 = 62%
```

**为什么这个数字最要紧**：那漏掉的 19 条，资料根本没送到模型眼前——prompt 写得再漂亮、模型换得再强，也救不回来，因为模型手里没这份材料。**所以 recall 决定的是效果天花板**；它上不去，其它优化都只是在剩下的 62% 里打转。

经验值：**recall@5 低于 80% 就说明检索环节有硬伤**，优先修检索（换 embedding、加混合检索、加 rerank），而不是去调 prompt。

**三个容易误解的地方**：

| 它不是 | 说明 |
| --- | --- |
| **不是"准确率"** | 只问"有没有"，不问"排第几"。正确资料排第 1 还是第 5，都算命中 |
| **不管多余的** | 5 条里有 4 条是废话，只要有一条对，照样算命中（多余结果由 precision 管） |
| **不等于答案正确** | recall 100% 也可能答错——资料给对了，模型却编了，那是 faithfulness 的问题 |

**@5 和 @20 要一起看**，能区分两种完全不同的病：

- 正确资料其实排在第 8 名 → `recall@5` 判"漏"，`recall@20` 判"命中"。这说明系统**找得到、排不准**，加个 rerank 把名次拉上来就行，不必换 embedding。
- `recall@5` 和 `recall@20` 都低 → 是真的找不到，问题在索引或 embedding 模型。

算法就是数比例：

```python
def recall_at_k(retriever, eval_set, k=5):
    hit = 0
    for item in eval_set:
        docs = retriever.invoke(item["question"])[:k]
        if any(item["source"] in d.metadata["source"] for d in docs):
            hit += 1
    return hit / len(eval_set)
```

**生成层**（用 LLM 当裁判，或 RAGAS 这类框架）：

这一层的指标都是"让另一个模型来打分"，所以叫 **LLM-as-judge**。它的分数不是绝对真理，但用来做**版本间对比**非常有效（A 版 0.82，B 版 0.87，说明 B 更好）。

| 指标 | 问的问题 |
| --- | --- |
| **Faithfulness（忠实度）** | 答案里的每句话，能在检索内容里找到依据吗？ |
| **Answer Relevance（相关性）** | 答案真的回答了用户的问题吗？ |
| **Context Precision** | 检回的内容里，有多少是真正有用的？ |

两个指标配合看，能直接定位病灶：

- recall 高 + faithfulness 低 → 资料找对了，模型在编 → 改 prompt / 加校验
- recall 低 + faithfulness 高 → 模型很老实，但资料没找到 → 改检索，别动 prompt

### 8.2 按症状定位，别乱改

这是最省时间的一张表：

| 症状 | 病灶在哪 | 该改什么 |
| --- | --- | --- |
| 答案完全跑题 | 检索 | 换 embedding / 加查询改写 / 混合检索 |
| 答案"差一点"，缺关键条件 | 切分 | 保住条款完整性 / 父子切分 |
| 检索到了但答案没用到 | 上下文组装 | 精简上下文、调整顺序、加"必须引用"约束 |
| 答案里有资料没说的内容 | 生成 | 强化"只用资料"约束 / 加答案校验 |
| 资料明明有却检不到 | 索引 | 检查该文档是否入库、是否被清洗误删、chunk 是否过碎 |
| 新旧制度答案冲突 | metadata | 加版本/时间过滤 |
| 简单问题答得很啰嗦 | 检索 | k 太大，降 k 或加 rerank 截断 |

### 8.3 迭代节奏

每次只改一个变量，改完重跑评估集，记录"改了什么 → 指标怎么变"。这个记录比代码更值钱——三个月后你会忘记为什么 chunk_size 是 400。

> ✅ **阶段 7 验收**：有一条命令能跑完评估、输出召回率与忠实度；每次改动都有可对比的数字。

## 九、阶段 8：上线与迭代

### 9.1 灰度

先在 10% 流量上线，重点看三件事：拒答率、点踩率、空召回率。三者任一异常就先回滚 collection 版本，而不是改代码。

### 9.2 bad case 回流

在 UI 上给每个答案一个"答得不对"按钮。点踩时自动记录：问题、检索到的 chunks、生成的答案。这一条产品设计带来的改进，通常比任何算法调优都有效——**因为你能看到真实用户怎么问**。

### 9.3 什么时候该升级架构

只有当评估数据明确指向"该查不查"（问题需要多步检索、或不该检索时它硬检索）时，才考虑 Agentic RAG。检索质量没做好就上 Agent，只会把"一次错"变成"三次错还更贵"。

## 附录 B：常见问题速查（按阶段）

按链路顺序排。**用法：先按"现象"找到那一行，再看根因——别跳过根因直接改后面。** 十次答错，有七次的病根在检索之前。

### B.1 数据与切分

| 现象 | 根因 | 解法 |
| --- | --- | --- |
| 解析出来满屏乱码、字黏在一起 | PDF 是扫描件，没有文本层；或用了粗糙的位置拼接 | 先用 `pdfplumber` 抽一页看有没有文本层，扫描件走 OCR；表格单独按表格解析，别混进正文 |
| 每个 chunk 开头都带"XX公司内部资料 第 X 页" | 页眉页脚跟着正文一起被切进去了 | 按页取首尾几行，正则匹配页码/公司名后删除；转 Markdown 时靠标题结构过滤 |
| 目录、修订记录、免责声明被当成知识 | 没做清洗 | 建黑名单整段丢弃：目录页、版本历史、页脚法务声明 |
| 答案总差一个条件（答"可以退"，漏了"跨境除外"） | 按字数硬切，切断了条款 | 按标题结构切；条款类文档以"第 X 条"为边界；兜底用父子切分（3.4） |
| 检回"最多结转 5 天"，但不知道是什么的 5 天 | chunk 太小，上下文丢失 | 父子切分：小块检索、大块喂模型（3.4） |
| 同一份文档导了三次，结果重复 | 没有稳定 ID，每次都是新增 | 内容 hash 派生 ID + 覆盖写入（4.3.1） |
| 文档改了，旧内容还在被检索 | 只插不删 | 按 `source` 先删后插（4.3.2） |

### B.2 索引与存储

| 现象 | 根因 | 解法 |
| --- | --- | --- |
| 换了 embedding 后效果断崖式下跌 | 只换了查询侧模型，索引还是旧模型建的 | 换模型必须全量重建，且建到新 collection（4.3.3） |
| 一部分文档永远检不到 | 入库时解析失败被静默跳过 | 入库后核对"文件数 vs 成功 chunk 数"，失败的单独列出来 |
| 结果里出现别的部门/客户的内容 | 没有 metadata 过滤，或在应用层才筛 | 权限字段进 metadata，检索时带 filter（5.5） |
| 新旧制度答案打架 | 两个版本同时可检索 | `version` 字段 + 只查当前版本，旧版标 archived |
| 数据到百万级后查询变慢 | 单机向量库、没调索引参数 | 换 Milvus/Qdrant，或调 HNSW/IVF 参数（4.2） |

### B.3 检索

| 现象 | 根因 | 解法 |
| --- | --- | --- |
| 答案完全跑题，检回的段落毫不相干 | 语义没匹配上：模型不适合中文/领域，或问题太口语 | 换中文强的模型（bge-m3、qwen3-embedding）先小样本验证；再加查询改写（5.4） |
| 型号、订单号、人名查不准 | 纯向量对精确字符串不敏感 | 加 BM25 混合检索（5.2） |
| 资料明明在库里，就是检不回 | 该文档没入库，或 chunk 切得太碎 | 先按 `source` 查库确认，再看切分结果 |
| 正确段落在 top-20，进不了 top-5 | 排序问题，不是召回问题 | 加 rerank（5.3） |
| 追问"那它多少钱"检不到东西 | 指代没消解，这句话本身没法检索 | 查询改写，带对话历史（5.4） |
| 总是漏同一类文档 | 切分破坏了结构，或 metadata 维度缺失 | 拿 10 个漏例人工看 chunk，多半是条件被切断 |
| 回答啰嗦还夹带无关信息 | k 太大，噪音进了上下文 | 降 k，或用 rerank 截到 5 条 |

### B.4 生成

| 现象 | 根因 | 解法 |
| --- | --- | --- |
| 编造资料里没有的内容 | prompt 没约束，或温度偏高 | "资料里没有就说未提及" + 温度调低（0~0.3）+ 要求引用（6.1） |
| 答了但不给出处 | prompt 没要求，上下文也没编号 | 上下文按 `[1][2]` 编号，要求答案标注来源（6.2） |
| 多段资料自相矛盾，模型随机信一个 | 新旧版本、重复 chunk 一起进了上下文 | 版本过滤 + 去重 + 按时间排序 |
| 关键信息在中间被忽略 | 长上下文"中间失忆" | 重要内容放首尾，压缩无关段落，别硬塞 |
| 简单问题答成小作文 | 没有长度约束 | 明确"不超过三句话"，或按问题类型分流 |

### B.5 工程与上线

| 现象 | 根因 | 解法 |
| --- | --- | --- |
| 说不清这次改动是好是坏 | 没有评估集，或改完没跑 | 30 条起步的评估集 + 改动前后分数（2.2） |
| 首字延迟三秒以上 | 串行调用：改写 → 检索 → rerank → 生成 | 能并行的并行（多查询），生成改流式 |
| 账单比预期高好几倍 | k 大、上下文长、重复调用 | 缓存改写结果、降 k、改写和校验用小模型 |
| 出问题回滚不了 | 在同一个 collection 上原地重建 | 版本化 collection + 配置切换（4.3.3） |
| 上线后才发现越权 | 权限只在前端或接口层做了 | 权限进 metadata，检索时强制过滤（5.5） |
| 检索还没修好就上了 Agentic | 想用架构复杂度弥补质量问题 | recall 上不去时，Agent 只是把"一次错"变成"三次错，还更贵"（9.3） |

### B.6 评估

| 现象 | 根因 | 解法 |
| --- | --- | --- |
| 指标不错，用户仍不满意 | 评估题是自己编的，和真实分布不符 | 从客服记录、点踩日志里捞问题（2.2） |
| 分数忽高忽低 | 样本太少，或裁判模型不稳定 | 扩到 50 条以上，固定裁判模型和 prompt，温度 0 |
| 不知道该改哪一层 | 检索和生成混在一起测 | 分层测：recall@k 与 faithfulness 分开（8.1） |

### B.7 排查顺序：倒着查，顺着改

用户报"答错了"，第一反应不该是改 prompt。按这个顺序倒查：

```text
答案不对
 ├─ 上下文里有正确段落吗？
 │    ├─ 有 ──► 生成层的问题：prompt 约束、上下文顺序、模型能力
 │    └─ 没有 ──► 往下查检索
 │         ├─ top-20 里有吗？
 │         │    ├─ 有 ──► 排序问题：加 rerank、降 k
 │         │    └─ 没有 ──► 召回问题
 │         │         ├─ 库里按 source 能搜到这段文字？
 │         │         │    ├─ 能 ──► embedding / 混合检索 / 查询改写
 │         │         │    └─ 不能 ──► 索引问题：没入库、被清洗、切碎了
```

**倒着查（从答案往数据追），顺着改（从数据往生成修）。** 顺序反了，就是在烂地基上刷漆。

三条纪律：

1. **一次只改一个变量**。同时换 embedding 又改 prompt，涨了你也不知道是谁的功劳。
2. **改完必须重跑评估集**。没有数字的优化不叫优化，叫赌博。
3. **先修数据，再修检索，最后调 prompt**。这三层的收益是数量级递减的。

## 结语

从 0 到 1 做 RAG，真正的分水岭不在模型选型，也不在框架用法，而在两件事：

**一是数据质量**——解析、清洗、切分做扎实，后面一切都顺；做马虎，后面怎么调 prompt 都救不回来。

**二是评估闭环**——先有评估集，再有优化。没有数字的优化，本质上是在赌。

至于混合检索、rerank、查询改写这些"高级技巧"，它们都是在这两件事做对之后才产生复利的。顺序错了，工具再好也没用。
